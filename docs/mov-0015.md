# MOV-0015: the 1 ms early-frame threshold and the update-event facing clock

[Issue #22](https://github.com/galitianu/warcraft-re/issues/22), following
[MOV-0014](mov-0014.md#next-experiment).

**Reference.** WC3 1.29.2 (9231), x86 32-bit, `wc3-1.29.2-9231-x86`, on the selected
Windows 11 Pro ARM64 VM.

**Questions.**

1. Every 1 ms frame exception so far is a callback less than 8 × 2⁻²⁴ s before a 5 ms
   frame, and it shows that frame's X/Y. MOV-0014 fitted that after capture. Is the
   threshold a fixed time, or the float32 frame time less a fixed offset?
2. Facing at an update frame does not follow X/Y. In MOV-0013/0014, callbacks that read
   ahead printed the facing from before the update. So did JASS-0001's 10 and 25 ms
   anomalies. Is facing set by the frame clock or by a separate 30 ms update clock?

## Design

Four [scenario v2](scenario-v2.md) files in [scenarios/MOV-0015](../scenarios/MOV-0015/).
Each is MOV-0014-a with a different `observe.start`. One Footman starts at (0, 0) facing 0
and is ordered to (1000, 0) at callback 0. Sampling is 1 ms for 1000 callbacks, with the
oracle-v1 1000 s library clock and the 10 s STATE clock. The schema, generator and
library are unchanged.

Each lag below is the time from a callback to the frame after its H0 frame, in units of
2⁻²⁴ s. That frame is an update frame when its index is 2 mod 6.

| Map | `start` | Informative callbacks |
|---|---|---|
| MOV-0015-a | 0.12 | 15–55 at lags 2–10 below 1 s; 40 (lag 7) before an update frame |
| MOV-0015-b | 0.45 | 40 (lag 1) before an update frame; 45, 50 (lags 2, 3); 55 (lag 8) past 1 s |
| MOV-0015-c | 0.999054 | 906, 911 (lags 4, 8) past 2 s; 781–901 after an update frame but before its 30 ms event |
| MOV-0015-d | 0.997001 | 28 (lag 2) and 33 (lag 8, an update frame) in [1, 2) |

Lags are multiples of 1, 2 and 4 units in [0.5, 1), [1, 2) and [2, 4).

## Hypotheses

**Frame.** Callback k has H0 frame n, `c(n) ≤ s(k) < c(n + 1)`, and reads frame n + 1 when:

| Rule | Condition |
|---|---|
| **H0** | never (footman-v4) |
| **T7** | `c(n + 1) − s(k) < 8 × 2⁻²⁴ s`, exactly |
| **Tsub** | `s(k) ≥ sub(c(n + 1), 7 × 2⁻²⁴)` in WC3's truncating float32 |

T7 and Tsub agree on every retained observation. In [1, 2), Tsub's subtraction
truncates to `c − 8 × 2⁻²⁴`, so a lag of 8 reads ahead. In [2, 4), the offset is below
the adder's range, and Tsub reads no frame early.

**Facing.** The update frames are 2 + 6j (0.51 s + 30 ms × j).

| Rule | Facing printed by a callback whose H0 frame is update frame n = 2 + 6j |
|---|---|
| **FH** | after the update (footman-v4) |
| **FU** | before the update while `s(k) < u(j)`, with `u(0) = 0.51`, `u(j + 1) = add(u(j), 0.03)` |

Elsewhere both rules print the H0 frame's facing. In particular, a callback that reads
the next frame's X/Y before an update keeps the earlier facing. FU is the "unit update
as a 30 ms event" candidate of [footman-v4 results](footman-v4-results.md#sampling-order),
written down exactly. `u(j)` equals `c(2 + 6j)` up to 1.98 s and is later from 2.01 s.
A rule where facing follows the X/Y frame is already refuted by MOV-0014-a's callback 40.

**Retained check** ([predictions.json](../results/mov-0015/predictions.json),
`retained_check`):

- T7 and Tsub reproduce every next-frame callback of MOV-0013 a–d and MOV-0014 a–c. They
  predict 15–35 for every retained 1 ms run; their extra 5 and 10 come before the unit
  moves. Neither moves a callback in any retained 10, 20, 25 or 50 ms schedule.
- FU predicts every facing of MOV-0013/0014. It also predicts every canonical JASS-0001
  10, 20, 25 and 50 ms facing, including the 25 that FH misses (p010 352–379, p025
  64–148). Where FU changes MOV-0001–0010's 20 ms schedule, from 10 s, footman-v4's
  sampled facing does not move.
- H0 and FH are each already refuted by the retained captures. They are kept as the
  baseline the C++ runner implements.

## Decision rules (fixed before capture)

- A frame rule survives only if, in all four maps, its list equals the observed set of
  callbacks whose STATE `x_9`/`y_9` equal frame n + 1, and no callback reads any other
  frame. A facing rule survives only if it predicts the STATE `facing_9` of every callback
  in all four maps.
- If **exactly one** of T7 or Tsub survives, the v2 runner adopts it, and so does the
  state comparison for the retained 1 ms runs. If FU survives and FH does not, both adopt
  FU. Each adopted rule must reproduce every retained capture. The before/after hashes
  are retained, and gated lists shrink only where the rule now predicts WC3.
- In every other case, or if no rule survives, the result is reported and gated as
  observed. No rule is fitted after capture.
