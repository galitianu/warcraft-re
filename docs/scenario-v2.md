# Scenario v2

Defined for [MOV-0013](mov-0013.md) / [issue #17](https://github.com/galitianu/warcraft-re/issues/17).
Version 2 is [scenario v1](scenario-v1.md) plus the two fields that experiment
needs. Every v1 rule (YAML subset, numbers, units, actions, provenance) applies
unchanged, and every v1 file keeps its v1 meaning. A v1 file containing a v2 field
is rejected. Parser: [Scenario.cpp](../tools/wc3test/Scenario.cpp). Files:
[scenarios/MOV-0013](../scenarios/MOV-0013/).

```yaml
schema: wc3-scenario
version: 2
experiment: MOV-0013
map_revision: MOV-0013-c
units:
  - name: u0
    type: hfoo
    position: [0, 0]
    facing: 0
observe:
  start: 0.02
  period: 0.001
  callbacks: 1000
  properties: [x, "y", facing, order]
  state_clock: 10
actions:
  - at: 0
    unit: u0
    order: move
    target: [1000, 0]
...
```

## New fields

| Field | Meaning |
|---|---|
| `observe.start` | Optional, default 0. Seconds after the setup (unit creation and watch, at the 0.5 s bootstrap) at which the library clock starts and callback 0 runs. Whole microseconds in [0, 1]. Every `at` time stays relative to callback 0. |
| `observe.state_clock` | Optional. The only accepted value is `10`. A 10 s one-shot clock starts at setup, after SETUP. Each callback ends, after its actions, with one `EVENT STATE` record: `c10_9`, `x_9`, `y_9` and `facing_9` (MOV-0012's format, R2SW(value, 1, 9)) for the single declared unit. It needs exactly one unit, and `start + callbacks × period` must stay below 10 s. |

## Generation

[oracle_codegen](../tools/oracle_codegen/main.cpp) emits `Generated by oracle_codegen v2`
and `scenario_version=2` in SETUP, followed by `start=` and `state_clock=`. A nonzero
start registers a single timer-event trigger, the same mechanism as the 0.5 s
bootstrap, whose action calls `OracleRun`. With start 0 it calls `OracleRun` directly,
as v1 does. v2 accepts the periods already captured with oracle-v1 (0.001, 0.01, 0.02,
0.025, 0.05 s). oracle-v1 itself is unchanged.

## Runner capability

`wc3test` runs a v2 scenario only with `--model v4 --phase after`, and only one
scenario per invocation. v1–v3 and the before-phase diagnostic stay v1 at 0.02 s.
The timing is the pre-registered rule H0 ([mov-0013.md](mov-0013.md)), implemented
in `run_scheduled` in [Cases.cpp](../tools/wc3test/Cases.cpp):

- Units are created and the movement clock starts at 0.5 s (frame 0). The sampler
  is scheduled at `s(0) = add(0.5, start)`, then `s(k) = add(s(k-1), period)`.
- A callback runs after every 5 ms frame with `c(n) <= s(k)` (a tie runs the frame
  first). It records samples, then its actions in file order, then STATE.
- TICK is `sub(1000, sub(add(s(0), 1000), s(k)))`; `c10_9` is
  `sub(10, sub(add(0.5, 10), s(k)))`.
- Identity: `observation_phase` is `scheduled-sampler-time`, with `sample_period_us`,
  `sampler_start_us` and `state_lag_us: null`.

The ten v1 scenarios, rewritten as version 2, give the same v4 samples, actions and
reported times as the v1 path ([test_mov0013.py](../tools/test_mov0013.py)). Every
v1 suite's payloads are unchanged
([runner-before-after.json](../results/mov-0013/runner-before-after.json)). The rule
is not WC3's in every case: MOV-0013 records where it differs. Those differences are
gated as observed, not modelled.
