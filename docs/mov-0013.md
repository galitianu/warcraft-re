# MOV-0013: sampler start phase and update order

[Issue #17](https://github.com/galitianu/warcraft-re/issues/17). **Question.** Does
the sampler's start phase relative to the movement updates explain which 5 ms frame
a 1 ms callback reads? These are the remaining footman-v4
[sampling-order differences](footman-v4-results.md#sampling-order).

**Reference.** WC3 1.29.2 (9231), x86 32-bit, `wc3-1.29.2-9231-x86`, on the selected
Windows 11 Pro ARM64 VM. MOV-0011 and JASS-0002 stay reserved for their own proposals.

## Retained observation to explain

All 27 retained 1 ms runs (JASS-0001-p001, MOV-0012) start the sampler, both clocks
and the move order together at the 0.5 s bootstrap. Frames advance a float32 clock
`c(n+1) = add(c(n), 0.005)` from 0.5 s. The sampler is scheduled at
`s(k) = add(s(k-1), 0.001)`. Every 5th callback (k = 5f) falls on a frame boundary,
and its float32 time is slightly *below* `c(f)`.

- Callback k = 5f reads frame f − 1, so it runs before frame f. At k = 10 and 40
  it reads the facing from before the update.
- The exceptions are f = 3…7 (k = 15, 20, 25, 30, 35), which read frame f. Frames 3–7
  lie strictly between the first two movement updates after the order (frames 2 and 8,
  i.e. 10 and 40 ms). The unit is stationary before frame 3, so k = 5 and 10 cannot
  show X/Y.
- One rule describes every retained period apart from these exceptions (checked
  against all 1/10/20/25/50 ms schedules before this capture). **H0:** a callback
  reads the latest frame with `c(n) ≤ s(k)`, and a tie runs the frame first.

## Design

Every variant is generated from one [scenario v2](scenario-v2.md) file in
[scenarios/MOV-0013](../scenarios/MOV-0013/). Each has one Footman `u0` at (0, 0),
facing 0, moved to (1000, 0), as in MOV-0012-a. Sampling is 1 ms for 1000 callbacks,
with the oracle-v1 1000 s library clock. A 10 s auxiliary clock starts at setup
(the 0.5 s bootstrap). Each callback ends with a `STATE` event in MOV-0012's format:
`c10_9`, `x_9`, `y_9` and `facing_9`, in R2SW_9. The aux clock therefore measures
each callback's time relative to the setup at 1e-6 s resolution.

| Map | `observe.start` | Order | Separates |
|---|---|---|---|
| MOV-0013-a | 0 | callback 0 | Control; must reproduce MOV-0012-a's observations exactly |
| MOV-0013-b | 0.0025 | callback 0 | No callback falls on a frame boundary |
| MOV-0013-c | 0.02 | callback 0 | Sampler and order move 20 ms against the 30 ms update grid |
| MOV-0013-d | 0 | callback 50 | The order moves 50 ms against the sampler start |

A delayed start uses the bootstrap's own mechanism, a single timer-event trigger at
`start` after setup. Variant c starts the sampler at callback 0's frame boundary
(`add(0.5, 0.02) = c(4)` exactly); variant b starts it inside a frame.

## Hypotheses and predictions (written before capture)

The frame numbers below assume the v4 update grid: updates at frames 2 + 6j
(10 + 30j ms after setup). If the first update instead follows the order by 10 ms,
X/Y onset shows it, and the order-relative column applies. A callback listed as an
exception reads frame `H0 + 1`. Exceptions only show where frames differ: once the
unit is moving (X/Y), or at an update frame whose facing changes.

| Hypothesis | a | b | c | d |
|---|---|---|---|---|
| **H0** scheduled-time order, no exception | none | none | none | none |
| **H1** tied to the sampler: its callbacks 15–35 | 15–35 | none | 25, 30, 35 visible (15, 20 stationary) | none visible (stationary) |
| **H2** tied to the order: frames between the first two updates after it (grid) | 15–35 | none | 25–45 | 75–95 |
| **H2′** as H2, with the first update 10 ms after the order | 15–35 | none | 15–35 | 65–85 |
| **H3** tied to absolute time: frames 3–7 after setup (0.515–0.535 s) | 15–35 | none | none visible | none visible |

Callback lists are k ≡ 0 (mod 5). Variant b tests every hypothesis's premise: none of
them predicts an exception where no callback is scheduled on a frame boundary.
Variant a is the reproduction gate. Any difference from MOV-0012-a's observations is a
generator or instrumentation finding, and stops interpretation of b–d.

Other expected observations, from the same scheduling model:

- TICK is the library clock, `sub(1000, sub(add(s(0), 1000), s(k)))`, where
  `s(0) = add(0.5, start)`. The aux clock is `c10_9 = sub(10, sub(add(0.5, 10), s(k)))`.
- Movement onset is the first frame after the first update that follows the order.
  On the grid this is frame 3 for a and b, frame 9 for c and frame 15 for d. An
  order-relative first update would put it at frame 7 for c and 13 for d.
- d's unit stays at (0, 0), facing 0 and order 0 until callback 50.

These are hypotheses about selection, not mechanisms. A result that matches no row
is reported as observed, with its first divergence from H0.

## Results

**Control.** MOV-0013-a's 3006 ordered observation records (TICK, SAMPLE, ACTION and
the STATE events' x/y/facing) equal MOV-0012-a's exactly. The generator and the
delayed-start-free path reproduce the hand-written capture.

**Frames read.** Each STATE event was matched against footman-v4's 1 ms state
sequence ([wc3states](../tools/wc3states/main.cpp), with the order at the C++ order
step). Every callback outside this table read the H0 frame.

| Map | Callbacks reading frame H0 + 1 | Movement onset | Hypotheses consistent |
|---|---|---|---|
| a | 15, 20, 25, 30, 35 | frame 3 (callback 15) | H0 ✗, H1, H2, H2′, H3 |
| b | none | frame 3 (callback 13) | all |
| c | 25, 30, 35 | frame 9 (callback 25) | H1 only |
| d | none | frame 15 (callback 76) | H0, H1, H3 |

c refutes H2 (predicted 25–45; 40 and 45 read the H0 frame), H2′ (onset is frame 9
on the grid, not 7) and H3 (0.545–0.555 s lies outside 0.515–0.535 s). d refutes H2
and H2′ (no exceptions at 65–95). **Only H1 matches all four:** the exceptions follow
the sampler's own callbacks 15–35, wherever the order and the update grid fall. The
movement onset follows the 30 ms global grid in all four maps.

**Mechanism candidate (post hoc, not implemented).** In a, c and d the sampler starts
on a frame boundary, and the next frame then lies exactly j float32 ulps (2⁻²⁴ s)
above callback k = 5j. That lag is the same in all three, so these captures cannot
separate "sampler callback 15–35" from "lag 3–7 ulps". WC3 ran the frame first at lags
3–7 and the sampler first at lags 8 and above (k = 40, 45 in c; the update at k = 40 in
a). At lag 2 (k = 10, an update frame in a) it ran the sampler first, so a single
"within n ulps" tolerance does not fit; separating the movement update from the frame
would. b has no callback within 41 943 ulps of a frame and shows nothing.

**Library clock (finding).** TICK reports `TimerGetElapsed` on the 1000 s timer.
a and d match the pre-registered `sub(1000, sub(add(s(0), 1000), s(k)))` exactly.
For the delayed starts it does not hold: 875 of b's 1001 TICKs and 624 of c's are
one ulp of the 1000 s clock (6.1035e-5 s) *below* the model, and callback 0 reads
`0.000061` instead of 0. The first canonical divergence is b's callback 6
(`0.006042` against `0.00610351562`, delta 6.1516e-5). That exceeds the unchanged
6.15e-5 tolerance, so b and c fail canonically on `t`. The x/y/facing values do not
depend on this clock, and the 10 s aux clock (`c10_9`) matches the sampler schedule
`sub(10, sub(add(0.5, 10), s(k)))` at every callback in all four maps.
Two post-hoc readings fit better; neither is implemented:

- The exact remaining time rounded down, `1000 − ⌊s(0) + 1000 − s(k)⌋`, misses 82
  (b) and 56 (c) TICKs, each one ulp above the model.
- Those residuals fit a timer whose start lies δ before `s(0)`, with δ in
  (5.126e-6, 5.186e-6] s for b and (3.278e-6, 3.338e-6] s for c. In both cases
  `s(0) mod 2⁻¹⁷` (5.1856e-6 and 3.3379e-6 s) is inside the interval, as if the timer
  were started at `s(0)` rounded down to 2⁻¹⁷ s. Two delays are not enough to tell
  this from a coincidence.

**C++ comparison.** The same scenario bytes run through
[wc3test](../tools/wc3test/Cases.cpp) (v2, footman-v4, rule H0), twice in separate
processes with identical bytes. The unchanged comparator and tolerances give:

| Map | Canonical | Exact text differences (R2SW_6 / R2SW_9) |
|---|---|---|
| a | FAIL: x at callback 15 (1.349609 vs 0) | x, y, STATE x_9/y_9 at 15–35 |
| b | FAIL: t at callback 6 (6.1516e-5 > 6.15e-5) | t at 875 TICKs, −1 ulp |
| c | FAIL: x at callback 25 | x, y, STATE x_9/y_9 at 25–35; t at 624 TICKs, −1 ulp |
| d | PASS | none |

These are honest mismatches against the pre-registered model; no reference or
tolerance changed. [run_mov0013.py](../tools/run_mov0013.py) requires exactly these
differences, pinning the TICK callback lists by count, direction and SHA-256. CI runs
it on every configuration and regrades the downloaded artifacts. Any new or missing
difference fails. Report: [results/mov-0013](../results/mov-0013/).

**Not migrated.** [compare_states.py](../tools/compare_states.py) keeps its
hand-copied MOV-0012 descriptions and its gate unchanged. Those maps are hand-written
JASS. v2 could describe d–g's units and orders but not their multi-timer CLOCKS
events, and a scenario file would imply generation provenance they do not have.

## Next experiments

1. Separate H1's callback index from float lag. Start the sampler on a frame
   boundary whose lag sequence differs from 1, 2, 3, … ulps (for example a start of
   at least 0.5 s, where the times pass 1 s and the float32 ulp doubles). Compute the
   lags with `wc3_float` before capture, and issue the order early enough that callbacks
   15–35 see a moving unit.
2. Test the 2⁻¹⁷ timer-start reading with delays whose `s(0) mod 2⁻¹⁷` differ
   widely (it predicts which TICKs move).
