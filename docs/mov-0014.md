# MOV-0014: sampler callback index or float32 lag, and the delayed timer start

[Issue #20](https://github.com/galitianu/warcraft-re/issues/20), following
[MOV-0013](mov-0013.md#next-experiments).

**Reference.** WC3 1.29.2 (9231), x86 32-bit, `wc3-1.29.2-9231-x86`, on the selected
Windows 11 Pro ARM64 VM.

**Questions.**

1. Which callbacks read the 5 ms frame after the one rule H0 selects? In every
   retained 1 ms run, and in MOV-0013-a/c, they are boundary callbacks 15–35. There
   the sampler's own callback index (H1) and the float32 lag before the frame (3–7
   ulps) coincide.
2. Does a delayed library clock start on a 2⁻¹⁷ s grid? MOV-0013-b/c fitted that
   after the fact.

## Design

Three [scenario v2](scenario-v2.md) files in [scenarios/MOV-0014](../scenarios/MOV-0014/).
Each is MOV-0013-c with a different `observe.start`: one Footman at (0, 0) facing 0,
moved to (1000, 0) at callback 0. Sampling is 1 ms for 1000 callbacks, with the
oracle-v1 1000 s library clock and the 10 s STATE clock. The schema, generator and
library are unchanged.

| Map | `start` | Callback 0 | Why |
|---|---|---|---|
| MOV-0014-a | 0.3 | 5 ulps (2⁻²⁴) after frame 60 | Same binade as MOV-0013; boundary lags 5 ulps smaller |
| MOV-0014-b | 0.72 | 6 ulps (2⁻²³) after frame 144 | Past 1 s, where the ulp doubles and lags grow 3 ulps per frame |
| MOV-0014-c | 0.9 | 7 ulps (2⁻²³) after frame 180 | As b; the two lag rules pick disjoint callbacks |

In all three, the sampler and the order start on a frame ≡ 0 (mod 6). The first
movement update after the order is therefore 10 ms later, as in MOV-0013-a. The first
moved frame, n₀ + 3, falls at boundary callback 15.

## Hypotheses

The lag is the time from callback k (H0 frame n, `c(n) ≤ s(k) < c(n+1)`) to frame n + 1.

| Frame rule | Callback k reads frame n + 1 when |
|---|---|
| **H0** | never |
| **H1** | k ∈ {15, 20, 25, 30, 35} and the lag is below 2⁻¹⁶ s |
| **Lu** | the lag is 3–7 ulps of the float32 time `s(k)` |
| **Ls** | the lag is 3–7 × 2⁻²⁴ s |

H1, Lu and Ls each reproduce MOV-0013 a–d exactly, and each predicts 15–35 for every
retained 1 ms run. None of them moves a callback in any retained 10, 20, 25 or 50 ms
schedule ([predictions.json](../results/mov-0014/predictions.json), `retained_check`).
Below 1 s, Lu and Ls are the same rule.

The library-clock rules give TICK = `TimerGetElapsed` of the 1000 s timer started
with the sampler at `s(0) = add(0.5, start)`:

| Clock rule | Reading |
|---|---|
| **M0** | `sub(1000, sub(add(s(0), 1000), s(k)))`, as MOV-0013 pre-registered; footman-v4's runner |
| **M1** | `sub(1000, ⌊s(0) + 1000 − s(k)⌋)`: exact remaining time, rounded down to float32 |
| **Q16/Q17/Q18** | M1 with the start `s(0)` rounded down to 2⁻¹⁶/2⁻¹⁷/2⁻¹⁸ s |
| **Qrel** | Q17 below 1 s, Q16 from 1 s: a quantum of 2⁷ ulps of `s(0)` |

Against the 2,002 MOV-0013 b/c TICKs, only Q17 and Qrel predict every one.

## Decision rules (fixed before capture)

- A frame rule survives only if, in all three maps, its list equals the observed set
  of callbacks whose STATE `x_9`/`y_9` equal frame n + 1, and no callback reads any
  other frame. A clock rule survives only if it predicts all 1001 TICKs of every map.
- If **exactly one** of Lu or Ls survives, the v2 runner adopts it. It must still
  reproduce every retained capture; the before/after hashes are retained, and gated
  lists shrink only where the rule now predicts WC3.
- If H1 alone survives, nothing is implemented. The effect is then tied to the
  callback index, with no mechanism.
- If exactly one clock rule survives, the v2 runner's library clock adopts it under
  the same conditions.
- In every other case, or if no rule survives, the result is reported and gated as
  observed. No rule is fitted after capture.
